# Инструкции для агентов

## Область действия

Этот файл применяется ко всему репозиторию Detailing Studio. Следуйте ему при изменении кода, контента, тестов и документации. Явные инструкции пользователя имеют приоритет; более локальные `AGENTS.md`, если появятся, уточняют правила для своих каталогов.

Общайтесь с пользователем и пишите документацию на русском языке. Идентификаторы, имена файлов и API оставляйте на английском в стиле существующего кода.

## Назначение и текущее состояние проекта

Detailing Studio — адаптивный русскоязычный лендинг детейлинг-студии в Москве. Это одностраничное приложение на маршруте `/`, с якорными переходами к разделам. В нём есть каталог услуг, галерея работ, описание студии, этапы работы, отзывы, форма и контакты.

В текущей реализации:

- Контент хранится в TypeScript-модулях и компонентах, CMS отсутствует.
- Нет API-маршрутов, базы данных, авторизации и серверной обработки заявок.
- Форма проверяет данные в браузере и показывает подтверждение заполнения. Она не отправляет данные, не сохраняет их в `localStorage` и не создаёт реальную запись на услугу.
- Услуги и галерея используют локальные WebP-изображения из `public/images/`.
- Для текущей версии переменные окружения не требуются.

Не описывайте демонстрационные возможности как подключённые интеграции. Не добавляйте сервер, CRM, аналитику или хранение персональных данных в рамках несвязанной задачи.

## Источники информации

Перед изменениями прочитайте относящиеся к задаче исходники и конфигурацию.

- `README.md` — описание проекта, установка, запуск и проверки.
- `CODEMAP.md` — дерево файлов, назначение модулей и связи компонентов.
- `package.json` — доступные команды и диапазоны версий зависимостей.
- `package-lock.json` — зафиксированные версии для установки.
- `tests/unit/logic.test.ts` и `tests/e2e/site.spec.ts` — существующие проверяемые сценарии.

Документация помогает ориентироваться, но фактическое поведение сверяйте с кодом. При изменении архитектуры, команд, структуры или пользовательских возможностей обновляйте соответствующие разделы документации.

## Архитектура и размещение изменений

### Страница и оформление

- `src/app/layout.tsx`: корневая разметка, `lang="ru"`, метаданные, шрифты и подключение CSS.
- `src/app/page.tsx`: композиция страницы, массивы преимуществ и этапов работы, описание студии, контакты и подвал.
- `src/app/globals.css`: общие токены, типографика, сетки, стили компонентов, адаптивность и CSS-анимации.
- `src/app/icon.svg`: иконка приложения.

Сохраняйте серверными компоненты, которым не нужны браузерные API или состояние. Добавляйте `"use client"` на минимально необходимой границе; не переводите всю страницу или корневой layout в клиентский режим ради отдельного интерактивного блока.

### Компоненты

- `src/components/layout/Header.tsx`: `Header`, `Logo`, мобильное меню и `MobileCTA`.
- `src/components/sections/Services.tsx`: категории и карточки услуг.
- `src/components/sections/Portfolio.tsx`: фильтры, раскрытие галереи и просмотр фотографий.
- `src/components/sections/Reviews.tsx`: карточки отзывов и состояние паузы ленты.
- `src/components/sections/LeadForm.tsx`: поля, ошибки, маска ввода и состояние успешного заполнения.
- `src/components/sections/lead-context.tsx`: общее состояние формы и выбор услуги из каталога.
- `src/components/ui/`: повторно используемые кнопки, анимации появления и декоративные эффекты.

Размещайте логику предметной секции в её компоненте. Выносите повторяющийся UI в `ui/`, чистые функции — в `lib/`, повторно используемую логику React — в `hooks/`. Не создавайте дополнительные слои абстракции для одноразового небольшого изменения.

## Правила реализации

- Используйте TypeScript, функциональные компоненты и хуки в принятом проектом стиле.
- Предпочитайте алиас `@/` для импортов из `src/`. Сохраняйте понятные локальные относительные импорты, если они уже используются рядом.
- Используйте `import type` для импортов, нужных только системе типов.
- Не отключайте strict mode, ESLint или проверки типов ради устранения ошибки. Избегайте необоснованных `any`, `@ts-ignore` и подавления правил.
- Сохраняйте существующие экспортируемые типы и интерфейсы, если задача не требует их изменения.
- Для динамических списков используйте устойчивые ключи, например идентификатор записи.
- Доступ к `window`, `document`, observers и canvas выполняйте только в клиентском контексте. Учитывайте серверный рендеринг и гидратацию.
- В эффектах удаляйте обработчики, отключайте observers и отменяйте `requestAnimationFrame`. Не оставляйте фоновые процессы после размонтирования.
- Сохраняйте изменения в пределах задачи. Не переформатируйте посторонние файлы и не выполняйте несвязанный рефакторинг.

## Форма и персональные данные

`src/lib/lead.ts` содержит тип `Lead`, начальное состояние, reducer, `formatPhone`, `validateLead` и `filterServices`. Общие поля формы хранятся в `LeadProvider`, ошибки валидации — локально в `LeadForm`.

Сохраняйте следующие сценарии, если пользователь явно не просит изменить их:

1. Выбор услуги в каталоге обновляет select формы, сбрасывает прежнее подтверждение и прокручивает к `#lead`.
2. Телефон форматируется как `+7 (999) 999-99-99`; ввод через `8`, вставка и последовательное удаление Backspace продолжают работать.
3. Проверяются непустое имя, допустимый телефон, существующая услуга и согласие. Текущий шаблон телефона сверяйте с `validateLead`, а не только с маской отображения.
4. При ошибках фокус получает первое некорректное поле, а сообщение связано с полем через ARIA.
5. Успешная проверка очищает поля и переводит фокус к подтверждению.
6. Повторное заполнение возвращает пустую форму и фокус в поле имени.

Не выводите имя и телефон в логи, не добавляйте их в URL, аналитику или браузерное хранилище. Если задача предусматривает реальную отправку, реализуйте явные состояния ожидания, ошибки и успешного ответа; сообщение об отправке должно соответствовать подтверждённому результату обработчика. Клиентская проверка не заменяет проверку на сервере при появлении backend.

## Навигация и интерактивные сценарии

Существующие якоря: `home`, `advantages`, `services`, `portfolio`, `about`, `process`, `reviews`, `lead`, `contacts`. Порядок меню определяется `navigation.ts` и может отличаться от порядка секций.

- При переименовании якоря обновляйте меню, ссылки, CSS, observers и тесты, которые на него ссылаются.
- `useActiveSection` определяет секцию под шапкой. На секциях вне меню предыдущая ссылка не должна оставаться активной.
- Сохраняйте корректность прямых URL с хешем, плавной прокрутки, ручной прокрутки и `aria-current="location"`.
- Мобильное меню должно закрываться по выбору пункта и Escape, возвращать фокус на триггер.
- Мобильная кнопка заявки скрывается, когда форма видима, и не должна перекрывать содержимое.
- Галерея должна сохранять фильтры, раскрытие, циклическое переключение, стрелки клавиатуры, свайпы, Escape и возврат фокуса к исходной карточке.
- Лента отзывов должна поддерживать ручную паузу и оставаться читаемой без анимации. Её дублирующие карточки не должны повторно озвучиваться или попадать в порядок фокуса.

## Дизайн, адаптивность и доступность

Сохраняйте существующее оформление, если задача не предполагает редизайн: тёмные и светлые секции, красный акцент `#d9252a`, Inter для основного текста и Manrope для заголовков. Переиспользуйте CSS-переменные, `.container`, `.section`, существующие классы и варианты `Button`.

- Проверяйте узкие экраны от 320 px; не допускайте горизонтального переполнения и перекрытия элементов фиксированными панелями.
- Используйте ссылки для переходов, кнопки для действий. Не заменяйте их кликабельными `div`.
- Сохраняйте семантические области страницы, иерархию заголовков, skip-link и видимый фокус.
- У полей должны быть связанные подписи, у кнопок с одной иконкой — понятные доступные имена.
- Для диалогов используйте имеющийся Radix Dialog и сохраняйте управление фокусом, заголовок и закрытие с клавиатуры.
- У содержательных изображений задавайте осмысленный `alt`; декоративные элементы скрывайте от вспомогательных технологий.
- Проверяйте контраст и читаемость текста поверх фотографий и эффектов.

## Анимации и производительность

- Учитывайте `prefers-reduced-motion` в CSS, Motion, canvas и tsParticles. При уменьшении анимации содержимое и действия должны оставаться доступными.
- Декоративные фоны должны оставаться `aria-hidden`, не перехватывать указатель и не выходить за пределы своей секции.
- Сохраняйте остановку фоновых эффектов вне области видимости и при скрытой вкладке, а также очистку ресурсов.
- Для tsParticles сохраняйте отложенную загрузку, повторное использование инициализации движка и клиентский рендеринг.
- Не добавляйте непрерывные обновления состояния React на каждый кадр для чисто декоративной отрисовки.
- Используйте `next/image` и корректный `sizes`. При `fill` контейнер должен задавать размеры и позиционирование.
- Высокий приоритет загрузки задавайте только изображениям, которым он нужен на первом экране.
- Сохраняйте локальные WebP и указывайте новые источники фотографий в `public/images/sources.json`.

## Команды и окружение

```sh
# Установка по lock-файлу
npm ci

# Разработка: http://localhost:3000
npm run dev

# Production
npm run build
npm start

# Статические проверки и unit-тесты
npm run typecheck
npm run lint
npm test

# Первоначальная установка браузеров для E2E
npx playwright install chromium firefox webkit

# E2E на production-сборке
npm run build
npm run test:e2e
```

`dev` и `start` привязывают сервер к `0.0.0.0`. Playwright обращается к `http://localhost:3000`, запускает `npm run start` и переиспользует уже работающий сервер. Перед E2E убедитесь, что он обслуживает актуальную версию проекта; наличие старого сервера может исказить результат.

`next/font/google` загружает шрифты во время сборки, поэтому ей нужен сетевой доступ к сервису Google Fonts. При сетевой ошибке сообщите точную причину ограничения; не утверждайте, что сборка прошла, и не меняйте шрифтовую систему без связи с задачей.

`npm run format` форматирует сразу `src`, `tests` и корневые TS/MJS/JSON-файлы, но не Markdown. Для небольших изменений запускайте Prettier адресно:

```sh
npx prettier path/to/changed-file --write
npx prettier README.md CODEMAP.md AGENTS.md --check
```

## Как выбирать проверки

Проверяйте изменение соразмерно его влиянию. Не заявляйте об успешной проверке без фактического запуска и чтения результата.

| Изменение                                  | Проверки                                                                                                |
| ------------------------------------------ | ------------------------------------------------------------------------------------------------------- |
| Только Markdown                            | Сверка фактов, путей и команд с кодом, Prettier для изменённых файлов, `git diff --check`               |
| Типы, чистая логика, данные                | `npm run typecheck`, `npm run lint`, относящиеся к изменению unit-тесты                                 |
| Компоненты и клиентское поведение          | Статические проверки, относящиеся unit/E2E-сценарии, проверка интерфейса                                |
| Стили, сетки, анимации                     | Статические проверки, визуальная проверка мобильного и широкого экрана, затронутые E2E и reduced motion |
| Сборка, зависимости, границы server/client | Статические проверки, unit-тесты, `npm run build`, затронутые E2E                                       |

Для выбора конкретного браузерного сценария можно использовать:

```sh
npm run test:e2e -- --project=chromium -g "часть имени теста"
```

Для общих изменений поведения проверяйте релевантные сценарии во всех трёх настроенных браузерах. При изменении поведения добавляйте или обновляйте проверку реального сценария, особенно для регрессий формы, навигации, фокуса и галереи. Для простых правок текста и документации новые тесты не нужны.

Существующие E2E проверяют ширины 320, 375, 390, 768, 1024, 1440 и 1920 px. Некоторые тесты используют CSS-классы, якоря, `data-service` и доступные имена: при изменении селекторов согласуйте тесты с новым интерфейсом, сохраняя смысл проверок. Не удаляйте проверки и не ослабляйте ожидания только ради зелёного результата.

## Работа с репозиторием и завершение задачи

1. Перед изменениями проверьте `git status --short`, чтобы отличать существующие правки от своих.
2. Прочитайте нужные модули и найдите их использования, прежде чем менять контракт.
3. Внесите минимальный согласованный набор изменений. Сохраняйте пользовательские правки, не перезаписывайте их ради чистого diff.
4. Обновите документацию и тесты, если изменились описанные возможности или поведение.
5. Выполните относящиеся к задаче проверки и просмотрите итоговый diff. Запустите `git diff --check`.
6. В ответе укажите результат, изменённые файлы, выполненные проверки и существенные ограничения. Незапущенные проверки называйте незапущенными.

Не редактируйте вручную `node_modules/`, `.next/`, `next-env.d.ts`, `*.tsbuildinfo` и артефакты тестов. Не добавляйте в Git секреты, `.env` с реальными значениями, логи и локальные настройки IDE. Не выполняйте сброс пользовательских изменений, очистку репозитория или переписывание истории без явного запроса. Коммит, push, публикацию и развёртывание выполняйте в рамках поручения пользователя.
